# AGENTS.md

An extension of the [Deno Standard Library](https://github.com/denoland/std),
published on JSR under the `@stdx` scope.

This file covers what an agent needs to work in the repo. Project policy
(dependencies, versioning, deprecations, contribution process, releases) is
described in [README.md](./README.md); follow it, and keep the two files from
contradicting each other.

## Repository layout

The repo is a Deno workspace of independently versioned and published packages.
Each package is a top-level directory listed in the `workspace` field of the
root `deno.json`. The other top-level directories (`_tools`, `_wasm`,
`coverage`, and dot-directories) are not packages.

```
<package>/
  deno.json   # name (@stdx/<package>), version, description, exports map
  README.md   # package docs
  mod.ts      # root module (only when the package has a "." export)
  *.test.ts   # colocated tests
  *.bench.ts  # optional benchmarks
  _wasm/      # generated wasm artifacts (committed)
```

- Public API goes in the `exports` map of the package's `deno.json`. Keep it in
  sync with the modules that exist — every public module should have a subpath
  export, and JSDoc examples must import from an export that exists.
- Package READMEs start with `# @stdx/<package>`, a short description, and then
  the entrypoints or examples.
- Shared types come from the std packages being extended (`@std/xml`,
  `@std/http`, ...). Never redeclare types that an upstream std package already
  provides.
- When adding a package or changing what one does, update its `README.md`, its
  `deno.json` `description`, and the root `README.md` (the "Packages" and
  "Package status" tables, and the `workspace` list in the root `deno.json`).
- `Releases.md` is generated by the `version_bump` workflow from commit
  messages. Do not edit it by hand; write good commit messages instead.

## Commands

Tasks are defined in the root `deno.json` and mirrored in `mise.toml`. CI runs
them through mise. If you change a task, change it in both files.

```sh
deno task check             # fmt --check (JS + Rust), lint, and deno check **/*.ts
deno task test              # full test suite with coverage
deno task fix               # format (JS + Rust) and auto-fix lint rules
deno task build:wasm        # build wasm crates into each package's _wasm/
deno task build:wasm:check  # verify committed wasm matches Rust sources
mise run check:pre-commit   # check, build:wasm:check, test, and publish dry run
```

`check` and `fix` also run `cargo fmt`, so they need the Rust toolchain
(installed by `mise install`).

Run `deno task check` and `deno task test` before considering work done. If you
touched Rust code in `_wasm/`, run `deno task build:wasm` and commit the
generated artifacts; CI verifies parity with `build:wasm:check`.

## Dependencies

See the "Dependencies" section of the README for the full policy. In short:

- JS: only `@std/*` and `@deno/*` packages, plus `@standard-schema/spec` and
  `@standard-schema/utils`. `@zod/zod` is allowed in tests only. Anything else
  needs to be agreed in an issue first.
- Rust (`_wasm/`): third-party crates are allowed case-by-case; workspace
  versions are pinned in `_wasm/Cargo.toml`.

## WASM

Wasm-backed modules are generated from the Rust workspace in `_wasm/`. Crate
names follow `<package>_<module>` (e.g. `crypto_hash_argon2`, `xml_xml`) and the
build script (`_tools/build_wasm.ts`) places output in `<package>/_wasm/` based
on that prefix. JS wrappers live in the package and are the public surface; the
`.mjs` bindings are an implementation detail.

## Conventions

- Formatting and linting are `deno fmt` and `deno lint`; Rust is `cargo fmt`.
  Never hand-format.
- New functionality needs colocated tests; aim for full line coverage of
  non-generated code.
- JSDoc examples should be valid, type-checkable code — examples are part of the
  published docs.
- Version bumps happen through the `version_bump` GitHub workflow, not by hand.
- When a function is adopted by the language, web standards, or Deno STD, mark
  it `@deprecated` and record it in `DEPRECATIONS.md`.
- Code copied from elsewhere must be credited, and only when its license allows
  it.

## Commits

Conventional commits, scoped by package: `feat(crypto): ...`, `fix(xml): ...`,
`chore: ...`. Use `!` for breaking changes (`feat(xml)!: ...`). The commit
messages become the entries in `Releases.md`.
